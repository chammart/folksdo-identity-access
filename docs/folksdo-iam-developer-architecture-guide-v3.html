1. IAM Overview

Folksdo IAM™ is the security boundary responsible for identity, tenant participation, and authorization.

Identity Service™

Who is the actor?

Global identity, authentication, sessions, verification, credential and password lifecycle.

Membership Service™

Where does the actor operate?

Identity-to-Tenant participation, invitation lifecycle and active Membership Context.

Access Service™

What may the actor do?

Permissions, roles, assignments, policies, restrictions and deterministic authorization.

3. Detailed Architecture & Components

A feature normally moves through these layers. Follow the existing capability's naming and composition patterns rather than bypassing a layer.

1 · HTTP Route
Fastify route registration in the standalone server or capability route module. Resolves authentication, trusted context, tenant/provider boundary and translates errors. apps/server/src/bootstrap/…
2 · API Contract
DTO, request/result contracts, Zod validation and public mapping. Zod failures must remain 400 validation_error. services/<capability>/src/api/…
3 · Use Case
Application orchestration and business operation. Calls capability-owned domain rules, read stores and Engine commit; does not embed transport concerns. services/<capability>/src/usecases/…
4 · Domain / Rules
Business invariants, lifecycle rules and deterministic decisions. Keep these capability-owned. services/<capability>/src/domain/…
5 · Runtime Composition
Wires repositories/adapters/use cases/API functions and lifecycle workers. services/<capability>/src/runtime/…
6 · Engine Commit
For canonical changes, commit canonical state + business event + outbox atomically. Include trusted request/correlation/actor/tenant metadata.
7 · Reactions
Other capabilities consume the event only when they own a consequence. A reaction updates the receiving capability's own state/projection; it does not mutate the source capability.
8 · Certification
Integration verifies real Engine/Mongo/NATS behavior; E2E verifies real HTTP/auth/context/authorization. Cross-capability certification proves the integrated contract. No HTTP mocks for production-grade provider certification.

5. How to Integrate a New Functionality

Use this sequence before digging through the repository. It is the shortest safe path from requirement to certified IAM behavior.

1
Name the business fact and owner.
Ask whether the feature changes WHO, WHERE or WHAT. If it is only a composed administration view, keep authority in the source capabilities.
2
Find the nearest existing use case in that capability.
Mirror its folder structure, contracts, runtime composition, error translation, metadata and test layout. Extend a proven pattern instead of creating a parallel framework.
3
Define the public contract and validation.
Add DTO/schema/result mapping. Reject invalid input through the standard validation contract. Never expose credential/session/token internals.
4
Implement the capability-owned use case.
Keep business rules out of Fastify. For writes, preserve lifecycle invariants, idempotency and deterministic outcomes.
5
Commit state/event/outbox atomically when state changes.
Reuse the Engine pattern and trusted metadata: requestId, correlationId, actorId, tenantId where applicable. Do not invent event names without checking the capability's current event convention.
6
Add reactions only for real downstream consequences.
The receiver owns its consequence. Avoid synchronous cross-service state mutation and avoid duplicating source truth.
7
Wire runtime and HTTP last.
Compose the use case in the capability runtime, expose the API, then register the route in the thin host. Cross-capability composition belongs at the host only when it is genuinely a composition concern.
8
Certify from the inside out.
Integration: real Engine + MongoDB + NATS. E2E: real HTTP + authentication + Membership context + Access authorization. Add a certification gate when the feature crosses capability boundaries.

Fast ownership decision

Authentication/session/security?
Start in services/identity.
Invitation/membership/tenant participation?
Start in services/membership.
Permission/role/assignment/authorization/review?
Start in services/access.
IAM-wide policy or operational projection?
Inspect existing host-owned IAM composition in apps/server/src/bootstrap. Keep underlying business authority in the three capabilities.
Cross-capability read?
Compose existing safe APIs/results; do not create a new canonical aggregate just to make the UI easier.
Extend safely
  • Mirror a neighboring capability use case.
  • Preserve deny-by-default authorization.
  • Use public DTO mappers for safe fields.
  • Keep Provider/Tenant authority explicit.
  • Use Engine atomic commits for canonical writes.
  • Test real infrastructure and reactions.
Avoid
  • Business logic in routes.
  • Direct cross-capability collection writes.
  • A generic admin capability owning IAM state.
  • Read projections becoming authoritative.
  • HTTP mocks as provider certification.
  • New event names or error envelopes by guesswork.

6. Runtime Security Chain

Identity authenticates→Membership resolves context→Access authorizes→Caller executes
Fail-closed rule A protected operation proceeds only after trusted identity, valid Membership Context, and sufficient Access authority have been established.

7. Core Runtime Architecture

Identity

Owns authentication truth. It does not decide tenant participation or permissions.

Membership

Owns participation and active context. It does not authenticate credentials or grant authority.

Access

Owns authorization truth. Permission definitions alone never imply a grant.

Fastify Host
  ├─ Identity runtime
  ├─ Membership runtime
  └─ Access runtime
        ↓
Folksdo Platform Runtime
        ↓
Folksdo Engine™ + MongoDB + NATS

IAM follows the state-first, event-replayable model. Canonical state changes and replayable business facts are committed through the shared Engine boundary; reactions consume facts because the receiving service owns a consequence.

11. Administration Read Foundation

Locally certified administration reads compose Identity, Membership and Access without creating a new authoritative IAM state source.

Ownership rule Identity administration remains Identity-owned, Membership administration remains Membership-owned, and Access administration remains Access-owned. Cross-capability People and IAM 360 responses are read composition only.

Tenant People

GET /api/v1/tenants/:tenantId/people

Tenant-authorized projection of safe Identity summary + Membership + active Roles + basic Access summary. Supports search, status, offset, limit.

Tenant Person Detail

GET /api/v1/tenants/:tenantId/people/:userId

Composes the person detail strictly inside the authorized tenant. Foreign-tenant access fails closed.

Provider IAM 360

GET /api/v1/admin/identities/:userId/iam-360

Provider-authorized cross-tenant view of safe Identity summary, Membership relationships, Roles, direct access, effective-access summary and safe security/session summary.

Safe Security Summary

Administration responses expose safe status/count/timestamp information only. They do not expose passwords, credential material, bearer tokens or provider session identifiers.

Authority separation Tenant administration authority never implies Provider authority. Provider IAM 360 and provider directories require explicit provider authorization; tenant People and Person Detail remain tenant-scoped.

API Authority Map

Use this view before integrating a UI or adding a new endpoint. APIs are grouped by who is allowed to call them, not by the implementation milestone that introduced them.

Permission rule. Public/self-service operations authenticate or act on the caller's own lifecycle and do not use Provider authority. Tenant Administration requires an active Membership in the target tenant plus the listed Access authority. Provider Administration requires explicit Provider authority; Tenant authority never implies Provider authority.

12. Events & Reactions

Identity → Access

User created, activated, disabled, archived and restored facts maintain Access-owned known identity state and authorization eligibility.

Membership → Identity

Invitation created, expired, revoked and redeemed facts maintain Identity's known-invitation projection.

Membership → Access

Membership created, activated, suspended, reactivated and archived facts maintain authorization lifecycle truth.

Reaction rule Cross-service reactions exist only when the receiving service owns the resulting consequence.
