1. Purpose & Promotion Rule

This document is the human QA gate after automated staging certification and before production promotion. The reference NorthRiver scenario establishes the useful business framing—Identity establishes who, Membership establishes where, and Access establishes what may be done—but this QA plan deliberately narrows the scope to IAM and turns those concepts into executable journeys.

QA must prove

  • A real invited NorthRiver user can establish an Identity and Membership.
  • Authenticated sessions resolve the correct actor.
  • Membership Context is tenant-scoped and lifecycle-aware.
  • Access allows explicit authority and denies absent authority.
  • Cross-tenant attempts cannot borrow NorthRiver authority.
  • Password and session security behave correctly.
  • Lifecycle and access changes converge without stale authority.

Promotion rule

P0 security cases: all PASS.

P1 business cases: all PASS unless an explicitly accepted release waiver exists.

Any unexpected 5xx, authority leak, cross-tenant leak, stale revoked session, or stale revoked access: NO-GO.

Do not “pass around” defects. A retry that later succeeds does not erase an unexplained security or consistency failure. Record the first failure and investigate.

3. NorthRiver QA Actors

NorthRiver Bank™

Administrator: Jordan — expected to have IAM administrative authority.

Ordinary member: Sarah — authenticated and active, without IAM administrative authority.

Invitee: Alex — starts without an established NorthRiver Membership.

Isolation tenant

Foreign user: Morgan — valid identity and membership in another tenant, but no NorthRiver membership or authority.

Use runtime-generated IDs from the staging fixture manifest. Friendly names are scenario labels, not authority.

4. Journey 1 — Invitation → Active NorthRiver Member

Proves the complete customer establishment path across Membership and Identity.

IAM-QA-001
Administrator creates a NorthRiver invitation
P1 Positive

Precondition: Jordan is authenticated in NorthRiver with invitation-management authority.

  1. Create an invitation for Alex using the Membership invitation API.
  2. Read/list the invitation as the authorized NorthRiver administrator.
  3. Confirm the invitation is scoped to NorthRiver and starts in the expected invitation lifecycle state.
Expected: Invitation is created once, belongs to NorthRiver, and is visible only through authorized NorthRiver context.
Capture: Invitation ID, tenant ID, status, HTTP status, request/correlation ID.
IAM-QA-002
Alex completes invitation sign-up and verification
P1 Positive

Precondition: A valid unused Alex invitation exists.

  1. Call POST /api/v1/identity/invitation-sign-up using the invitation contract.
  2. Complete email verification using the QA verification mechanism.
  3. Sign in as Alex.
Expected: Identity is established and verified; invitation choreography converges; Alex can authenticate without manually creating IAM state.
Capture: Identity ID, invitation ID, membership ID/status, session identifier fingerprint only, correlation IDs.
IAM-QA-003
Redeemed invitation cannot establish a second account
P0 Negative

Precondition: IAM-QA-002 completed.

  1. Attempt to reuse the same invitation for another sign-up/redeem operation.
Expected: Request is rejected deterministically; no duplicate Identity or Membership is created.
Capture: HTTP status/error code and proof that resource counts/IDs did not duplicate.

5. Journey 2 — Sign-In & Session Truth

Proves Identity authentication and session read behavior.

IAM-QA-004
Valid NorthRiver user signs in and reads self
P1 Positive

Precondition: Sarah is verified and active.

  1. Sign in with Sarah’s valid credentials.
  2. Call GET /api/v1/identity/session.
  3. Call GET /api/v1/identity/me.
Expected: Session and user reads resolve Sarah consistently; no tenant authority is inferred merely from Identity.
Capture: HTTP statuses, identity ID, session metadata, request IDs.
IAM-QA-005
Invalid credentials fail without session creation
P0 Negative

Precondition: Sarah exists.

  1. Attempt sign-in with an incorrect password.
  2. Attempt to use any returned/previously absent session artifact from the failed request.
Expected: Authentication fails and no usable session is created.
Capture: HTTP status/error code; confirm no authenticated session.

6. Journey 3 — Membership Context

Proves “where the actor operates” is explicit and tenant-scoped.

IAM-QA-006
Active Sarah resolves NorthRiver Membership Context
P1 Positive

Precondition: Sarah has an active NorthRiver Membership and valid session.

  1. Call GET /api/v1/membership/current in NorthRiver context.
  2. If supported by the deployed contract, select/set NorthRiver via POST /api/v1/membership/context.
  3. Read current context again.
Expected: The resolved context references Sarah’s NorthRiver Membership and tenant; context is stable across subsequent protected requests.
Capture: Tenant ID, membership ID/status, context response, correlation ID.
IAM-QA-007
Identity without NorthRiver membership cannot manufacture context
P0 Negative

Precondition: Morgan is authenticated but has no NorthRiver Membership.

  1. Attempt to select or resolve NorthRiver Membership Context using Morgan’s session and NorthRiver identifiers.
Expected: 403 fail-closed; identifiers alone do not establish membership or authority.
Capture: HTTP status/error code, foreign identity ID, targeted tenant ID.

7. Journey 4 — Administrator Authority

Proves explicit Access authority produces allowed decisions.

IAM-QA-008
Jordan receives allow for an IAM administrative action
P0 Positive

Precondition: Jordan is authenticated, active in NorthRiver, and holds the fixture-defined administrator authority.

  1. Resolve Jordan’s NorthRiver context.
  2. Call POST /api/v1/access/authorize for the QA fixture’s administrative permission/action.
  3. Execute the corresponding protected IAM operation where the public API supports it.
Expected: Authorization is allowed and the protected operation succeeds only under Jordan’s trusted context.
Capture: Permission/action key, authorization decision, membership/tenant IDs, operation status.

8. Journey 5 — Ordinary Member Denial

Proves deny-by-default and prevents privilege borrowing.

IAM-QA-009
Sarah is denied the same administrator action
P0 Negative

Precondition: Sarah is active in NorthRiver but lacks the administrator authority used in IAM-QA-008.

  1. Resolve Sarah’s NorthRiver context.
  2. Call authorization for the same administrative permission/action.
  3. Attempt the protected administrative operation.
Expected: Authorization is denied and protected execution returns 403; no state mutation occurs.
Capture: Decision, HTTP status/error code, before/after target state.
IAM-QA-010
Unknown/unassigned permission is not implicitly granted
P0 Negative

Precondition: Sarah has a valid NorthRiver context.

  1. Request authorization for a permission/action not effectively assigned to Sarah.
Expected: Deterministic deny. Permission existence or naming does not grant access.
Capture: Authorization request and denial response.

9. Journey 6 — Cross-Tenant Isolation

Proves tenant boundaries cannot be crossed with valid credentials.

IAM-QA-011
Foreign member cannot use NorthRiver identifiers
P0 Negative

Precondition: Morgan is valid in the isolation tenant.

  1. Authenticate Morgan.
  2. Target NorthRiver Membership/Access resources using known NorthRiver IDs.
  3. Attempt NorthRiver authorization using Morgan’s identity/session.
Expected: NorthRiver context and authority are rejected. No NorthRiver membership, role, assignment, or protected data is exposed.
Capture: HTTP statuses, targeted IDs, correlation IDs; redact sensitive response data.
IAM-QA-012
NorthRiver authority does not leak to another tenant
P0 Negative

Precondition: Jordan is a NorthRiver administrator but lacks equivalent authority in the isolation tenant.

  1. Authenticate Jordan.
  2. Switch/target the isolation tenant without a valid membership/authority there.
  3. Attempt the same administrative authorization used in IAM-QA-008.
Expected: Jordan’s NorthRiver authority is not portable; foreign-tenant operation is denied.
Capture: Tenant IDs, authorization decision, HTTP status.

10. Journey 7 — Membership Lifecycle

Proves membership lifecycle changes affect context and authority.

IAM-QA-013
Deactivated member loses usable NorthRiver context
P0 Negative

Precondition: Sarah is active and her current session works. Jordan can perform the supported membership lifecycle administration.

  1. Deactivate Sarah’s NorthRiver Membership using the deployed Membership contract.
  2. Using Sarah’s existing session, resolve NorthRiver Membership Context.
  3. Attempt a NorthRiver protected action.
Expected: Identity session may still identify Sarah, but inactive Membership cannot provide valid NorthRiver operating authority; protected operation is denied.
Capture: Membership status transition, context result, authorization result.
IAM-QA-014
Reactivated member regains only assigned authority
P1 Positive

Precondition: IAM-QA-013 completed and the deployed lifecycle supports reactivation.

  1. Reactivate Sarah’s Membership.
  2. Resolve NorthRiver context again.
  3. Verify ordinary allowed behavior works.
  4. Re-run the administrator action denial.
Expected: Context becomes usable again, but reactivation does not create administrator authority.
Capture: Membership status, allowed ordinary action, denied admin action.

11. Journey 8 — Invitation Failure Paths

Proves invitation lifecycle is secure and deterministic.

IAM-QA-015
Revoked invitation cannot be redeemed
P0 Negative

Precondition: Jordan creates a fresh invitation and revokes it using the supported Membership contract.

  1. Attempt Alex-style sign-up/redeem with the revoked invitation.
Expected: Rejected; no Identity/Membership establishment occurs from the revoked invitation.
Capture: Invitation status, HTTP status/error, no-new-resource evidence.
IAM-QA-016
Expired invitation cannot be redeemed
P0 Negative

Precondition: Use the deterministic expired-invitation QA fixture.

  1. Attempt invitation sign-up/redeem with the expired invitation.
Expected: Rejected deterministically; no membership authority is created.
Capture: Invitation ID/status, HTTP status/error.

12. Journey 9 — Password Lifecycle

Proves password reset/change flows preserve authentication security.

IAM-QA-017
Password reset completes and old password stops working
P0 Positive

Precondition: Sarah has a verified Identity and QA can obtain the reset artifact through the approved test mechanism.

  1. Call POST /api/v1/identity/password-reset/request.
  2. Complete POST /api/v1/identity/password-reset.
  3. Attempt sign-in with the old password.
  4. Sign in with the new password.
Expected: Old password is rejected; new password authenticates Sarah.
Capture: Statuses and identity ID; never record reset token or passwords.
IAM-QA-018
Authenticated change-password rotates credentials
P0 Positive

Precondition: Sarah is authenticated with the current password.

  1. Call POST /api/v1/identity/change-password.
  2. Sign out if required by contract.
  3. Verify previous password is rejected and changed password succeeds.
Expected: Credential rotation is effective and deterministic.
Capture: Statuses only; no password values.

13. Journey 10 — Session Revocation

Proves sign-out removes continued authenticated use.

IAM-QA-019
Signed-out session cannot access protected IAM reads
P0 Negative

Precondition: Sarah has a valid session.

  1. Confirm GET /api/v1/identity/session succeeds.
  2. Call POST /api/v1/identity/sign-out.
  3. Reuse the same session credential against session/me and a protected IAM operation.
Expected: The revoked/signed-out session is rejected; no protected operation succeeds.
Capture: Pre/post statuses and correlation IDs; do not paste bearer token.

14. Journey 11 — Access Change Convergence

Proves authority changes take effect and do not remain stale.

IAM-QA-020
Grant becomes effective for the intended NorthRiver member only
P0 Positive

Precondition: Sarah is active and currently denied the selected QA administrative permission. Jordan can manage the fixture-defined access assignment.

  1. Create the supported role/permission assignment for Sarah.
  2. Re-run authorization for Sarah.
  3. Verify Morgan remains denied for NorthRiver.
Expected: Sarah becomes allowed only after the authoritative assignment; Morgan remains denied.
Capture: Assignment ID, permission/action, before/after decisions.
IAM-QA-021
Revocation removes previously effective authority
P0 Negative

Precondition: IAM-QA-020 completed.

  1. Remove/revoke the assignment using the supported Access contract.
  2. Using Sarah’s existing authenticated session/context, re-run authorization.
  3. Attempt the protected operation.
Expected: Previously granted authority is no longer effective; operation is denied without requiring identity recreation.
Capture: Revocation result, denial decision, protected operation status.

15. Journey 12 — Fail-Closed Security Boundary

Final adversarial sweep of the IAM request chain.

IAM-QA-022
Missing authentication is rejected before business execution
P0 Negative

Precondition: None.

  1. Call a protected Membership or Access operation without authentication.
Expected: 401; no protected business mutation occurs.
Capture: HTTP status/error and target state unchanged.
IAM-QA-023
Malformed IAM request returns validation_error
P1 Negative

Precondition: Use an authenticated actor where required.

  1. Submit a structurally invalid request to a representative Identity/Membership/Access endpoint.
Expected: 400 with stable validation_error; no stack trace/provider/database internals are exposed.
Capture: HTTP status, public error envelope.
IAM-QA-024
Tampered/unknown identifiers do not bypass the chain
P0 Negative

Precondition: Sarah is authenticated.

  1. Use syntactically valid but unknown/foreign membership, role, assignment, or tenant identifiers in a protected flow.
Expected: Request fails safely according to the endpoint contract; no authority is inferred from IDs and no foreign state is disclosed.
Capture: HTTP status/error, correlation ID, targeted resource type.

16. Final Regression Sweep

Identity

  • Invitation sign-up
  • Email verification
  • Sign in / sign out
  • Current session / current user
  • Password reset
  • Change password

Membership + Access

  • Invitation lifecycle
  • Current Membership Context
  • Active/inactive lifecycle enforcement
  • Explicit allow
  • Deny-by-default
  • Cross-tenant isolation
  • Grant/revoke convergence
Regression ruleRun the existing automated IAM certification before this human QA session. Human QA does not replace integration, reaction, E2E, Bruno, or staging certification; it validates the release candidate as a real NorthRiver journey.
