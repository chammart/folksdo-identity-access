1. IAM Overview

Folksdo IAM™ is the security boundary responsible for identity, tenant participation, and authorization.

Identity Service™

Who is the actor?

Global identity, authentication, sessions, verification, credential and password lifecycle.

Membership Service™

Where does the actor operate?

Identity-to-Tenant participation, invitation lifecycle and active Membership Context.

Access Service™

What may the actor do?

Permissions, roles, assignments, policies, restrictions and deterministic authorization.

2. Runtime Security Chain

Identity authenticates→Membership resolves context→Access authorizes→Caller executes
Fail-closed rule A protected operation proceeds only after trusted identity, valid Membership Context, and sufficient Access authority have been established.

3. Architecture

Identity

Owns authentication truth. It does not decide tenant participation or permissions.

Membership

Owns participation and active context. It does not authenticate credentials or grant authority.

Access

Owns authorization truth. Permission definitions alone never imply a grant.

Fastify Host
  ├─ Identity runtime
  ├─ Membership runtime
  └─ Access runtime
        ↓
Folksdo Platform Runtime
        ↓
Folksdo Engine™ + MongoDB + NATS

IAM follows the state-first, event-replayable model. Canonical state changes and replayable business facts are committed through the shared Engine boundary; reactions consume facts because the receiving service owns a consequence.

7. Events & Reactions

Identity → Access

User created, activated, disabled, archived and restored facts maintain Access-owned known identity state and authorization eligibility.

Membership → Identity

Invitation created, expired, revoked and redeemed facts maintain Identity's known-invitation projection.

Membership → Access

Membership created, activated, suspended, reactivated and archived facts maintain authorization lifecycle truth.

Reaction rule Cross-service reactions exist only when the receiving service owns the resulting consequence.
