This guide demonstrates how the Folksdo Operations™ Identity Service behaves in a realistic enterprise SaaS onboarding and credential-lifecycle scenario using NorthRiver Bank™, a large North American financial institution.

Scenario Overview

NorthRiver Bank has signed an enterprise SaaS contract with Folksdo. A Folksdo operator provisions the tenant and sends an invitation to the bank's first administrator. 

Sarah Carter
VP Transformation Office
NorthRiver Bank
sarah.carter@northriverbank.com

Sarah's Identity lifecycle includes:

  • receiving a tenant invitation
  • signing up using the invitation token
  • verifying email ownership
  • activating her global Identity
  • signing in and creating an authenticated session
  • retrieving her current session
  • retrieving her current global Identity profile
  • requesting password recovery when required
  • resetting a password through the recovery flow
  • changing a password while already authenticated
  • signing out and ending the active session
Identity owns Sarah's global Identity, authentication, sessions, and credential lifecycle. Membership later establishes which tenant context she operates in, and Access determines what she is authorized to do there.

Use Case 1

Invitation SignUp™

Sarah clicks the invitation link received from Folksdo and creates her global Identity.

Request

POST /api/v1/identity/invitation-sign-up
Content-Type: application/json

{
  "invitationToken": "invite_nr_bank_001",
  "firstName": "Sarah",
  "lastName": "Carter",
  "password": "StrongPassword123!"
}

Business Rules

  • validate invitation token
  • resolve invitation lifecycle state
  • create or reuse the global Identity
  • create a pending email verification
  • coordinate verification-token mechanics
  • persist replayable business events
  • persist matching outbox messages

State Changes

IdentityUser created or reused
Identity profile created
EmailVerification created → pending
Invitation redemption requested

Business Events

identity.user_created
identity.user_profile_created
identity.email_verification_requested
identity.invitation_redemption_requested

Result

Sarah's global Identity exists
Email verification is required
Invitation redemption has been requested

Use Case 3

Sign In™

Sarah signs in after her email is verified and her global Identity is active.

Request

POST /api/v1/identity/sign-in
Content-Type: application/json

{
  "email": "sarah.carter@northriverbank.com",
  "password": "StrongPassword123!"
}

Business Rules

  • validate request shape
  • delegate credential authentication to BetterAuth
  • reject invalid credentials without leaking account existence
  • confirm the Identity is active and verified
  • create Identity-owned active session lifecycle state
  • persist the replayable session event and outbox message

Business Events

identity.session_created

Example Response

{
  "userId": "usr_sarah_001",
  "email": "sarah.carter@northriverbank.com",
  "sessionId": "ses_sarah_001",
  "expiresAt": "2026-07-02T13:05:00.000Z"
}

Result

Authenticated session created
Use Case 5

Current Session™

Sarah's client resolves the currently active Identity session through a safe session reference such as x-identity-session-id.

Request

GET /api/v1/identity/session
x-identity-session-id: ses_sarah_001

Business Rules

  • resolve the current active session
  • return only Identity-owned safe session state
  • exclude provider tokens, cookies, secrets, and internal BetterAuth details
  • do not resolve Membership context
  • do not perform Access authorization

Example Response

{
  "sessionId": "ses_sarah_001",
  "userId": "usr_sarah_001",
  "status": "active",
  "createdAt": "2026-07-02T12:05:00.000Z",
  "expiresAt": "2026-07-02T13:05:00.000Z"
}

Result

Current authenticated Identity session returned safely
Use Case 6

Current User™

With an active session, Sarah's client retrieves her current global Identity and Identity-owned profile.

Request

GET /api/v1/identity/me
x-identity-session-id: ses_sarah_001

Business Rules

  • resolve the active authenticated session
  • resolve the associated global Identity
  • return Identity-owned user and profile fields
  • exclude memberships, roles, permissions, tenant access, credentials, and provider secrets

Example Response

{
  "userId": "usr_sarah_001",
  "email": "sarah.carter@northriverbank.com",
  "firstName": "Sarah",
  "lastName": "Carter",
  "status": "active",
  "emailVerified": true
}

Result

Current global Identity returned
Membership and Access boundaries preserved

Use Case 9

Change Password™

While authenticated, Sarah proactively changes her password without entering the password-recovery flow.

Request

POST /api/v1/identity/change-password
Content-Type: application/json
x-identity-session-id: ses_sarah_001

{
  "currentPassword": "RecoveredPassword456!",
  "newPassword": "NorthRiverSecure789!"
}

Business Rules

  • require an active authenticated session
  • resolve the authenticated global Identity
  • validate the current credential through BetterAuth
  • apply the replacement credential through BetterAuth
  • record the credential lifecycle update
  • persist identity.credential_updated and matching outbox state
  • preserve the active session according to Identity session policy

Business Events

identity.credential_updated

Example Response

{
  "userId": "usr_sarah_001",
  "status": "updated",
  "changedAt": "2026-07-02T12:40:00.000Z"
}
Change Password™ and Reset Password™ are intentionally separate. Change Password™ requires an authenticated session and the current credential. Reset Password™ is a recovery flow driven by a reset token.

Sign Out™

Sarah signs out after finishing her work session.

Request

Business Rules

  • validate the session reference
  • resolve the active Identity session
  • ask BetterAuth to revoke or end the provider session
  • mark the Identity session as signed_out
  • persist the replayable session-ended event
  • persist the matching outbox message atomically

State Changes

IdentitySession
active → signed_out

Business Events

identity.session_ended

Result

Sarah Carter session ended
Session is no longer active

Atomic Commit Guarantee

Identity Service does not treat durable Identity mutations as partial business writes. State, replayable events, and outbox messages cross the Folksdo Engine™ commit boundary together. 

State Changes
      +
Replayable Events
      +
Outbox Messages
      =
One Engine state.commit(...)

Examples:

Verify Email™

EmailVerification update
+
Identity activation
+
identity.user_email_verified
+
identity.user_activated
+
matching outbox messages
=
one commit


Sign In™

Identity session state
+
identity.session_created
+
matching outbox message
=
one commit


Credential Lifecycle™

Identity credential lifecycle state
+
identity.password_reset_requested / identity.credential_updated
+
matching outbox message
=
one commit where Identity state is mutated
